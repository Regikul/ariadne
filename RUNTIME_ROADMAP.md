# План реализации локального runtime

Спецификация: [okf/design/local-runtime.md](okf/design/local-runtime.md).
Связанные контракты: [DSL графа](okf/design/graph-dsl.md),
[узел](okf/design/node.md), [время](okf/design/time.md).

Цель — реализовать пакетный `ari_local_runtime`, исполняющий весь граф
в вызывающем Erlang-процессе, с отслеживанием прогресса и уведомлениями.

## Правила отслеживания прогресса

- [ ] — задача не начата.
- [~] — задача начата, но не завершена.
- [x] — задача завершена и проверена.

Перед началом работы менять отметку задачи на `[~]`. Отмечать `[x]` только
после выполнения задачи и относящихся к ней проверок. Этап считается начатым,
когда начата хотя бы одна его задача, и завершённым, когда завершены все его
задачи и выполнен критерий завершения этапа.

Если работа остановилась, оставлять `[~]` и кратко указывать под задачей
текущее препятствие или оставшуюся работу. При возобновлении актуализировать
заметку, после устранения препятствия удалять её. Не накапливать историю
обсуждений и устаревшие статусы. Изменение объёма работ отражать в самих задачах.

Этапы выполнять последовательно. Тесты добавлять вместе с соответствующей
реализацией. Проверки Erlang запускать через `./silent_rebar3`.

Каждый этап заканчивается сверкой со спецификацией: расхождения, принятые
по ходу этапа, вносятся в `local-runtime.md` до отметки `[x]` у этапа.
Этап 7 содержит только сквозную вычитку.

## Принятые решения

- Сводки путей живут в `ari_vtime`: они разбирают внутренности opaque `t()`.
- Проверка допустимости уведомлений — чистые функции модуля `ari_progress`.
- Состояние программы и прогона наблюдается через `inspect/1`, возвращающий
  map. Записи `#program{}` и `#execution{}` остаются внутренними, тесты и
  пошаговая трассировка читают map.
- Тестовые узлы — модули в `test/nodes`. Поведение внутри модуля выбирается
  через `Args`; сценарию с особым поведением полагается свой модуль.
  `ari_test_node` переезжает туда же.

### Оптимизации в порядке ожидаемой выгоды

Порядок учитывает ожидаемое ускорение на обнаруженных нагрузках и сложность
реализации. Каждую оптимизацию проверять отдельно: сравнивать замеры до и
после на одинаковых нагрузках, запускать тесты корректности, обновлять
описание действующего алгоритма и его сложности. Если замеры меняют приоритеты,
переупорядочивать оставшиеся задачи.

1. [x] Пропускать пересчёт прогресса, когда нет запросов, ожидающих постановки
   в `ready`. Сделано счётчиком `#execution.pending` непоставленных запросов.
   `advance/2` для узла с начальными запросами `{I, [N-I]}` при N=800:
   1274 мс → 0,34 мс, рост стал линейным. В пункте 4 счётчик заменён
   списком кандидатов: без кандидатов проверять нечего.

2. [x] Накапливать нарушения добавлением в голову списка, разворачивая его
   в `violations/1` и `inspect/1`. Сделано; порядок выдачи проверяют
   существующие тесты результатов и сквозной сценарий с нарушениями.
   `time_rule` на каждом сообщении при 10 000 сообщений: 7,9 → 0,3 мкс/шаг,
   стоимость шага от числа нарушений больше не зависит.

3. [x] Заменить последовательную вставку в антицепь построением фронтира
   через сортировку и линейный проход. Сделано гибридом: вставка до ширины
   восемь, дальше `ari_vtime:sort/1` (эпоха, затем итерации от внешнего
   цикла) и один проход. Полная замена вставки сортировкой отвергнута по
   замерам: узкий фронтир из 1000 ключей дорожал с 6 до 27 мкс/шаг.
   `new/2` при 800 несравнимых запросах: 24,4 → 18,2 мс; остаток — проверка
   N запросов против фронтира ширины N, пункт 4. Совпадение с определением
   проверено на всех подмножествах сеток глубины один и два и на случайных
   широких антицепях.

4. [x] Сократить полный перебор ожидающих уведомлений. Сделано свидетелями
   блокировки: заблокированный запрос помнит время фронтира, на котором
   проверка остановилась, и возвращается в кандидаты при его исчезновении;
   меньшее время, вытеснившее свидетеля, наследует его список. Фронтиры
   хранятся в `#execution{}`, узел с исчезнувшим временем помечается
   `stale` и пересобирается перед следующей проверкой; до первого запроса
   в прогоне фронтиры не поддерживаются. Сводки берутся один раз на
   узел-источник, источник без пути пропускается целиком. Убывающие времена
   при 1000 сообщениях: 51 → 7 мкс/шаг; `new/2` при 800 несравнимых
   запросах: 18,2 → 0,3 мс. Инварианты свидетелей и фронтиров проверяются
   в сквозных тестах после каждого шага. Остаток роста — обход всех ключей
   `counts` при пересборке фронтира одного узла, пункт 5.

5. [x] Сгруппировать `counts` по узлам, чтобы пересборка фронтира одного
   узла обходила только его ключи. Сделано: `counts()` стал
   `#{Node => #{Time => Count}}`, фронтир сообщений помечается устаревшим
   только при исчезновении минимального времени. Убывающие времена при
   1000 сообщениях: 7,1 → 1,7 мкс/шаг, рост на шаг исчез; пропускная
   способность без запросов выросла с 1,4–2,0 M до 2,0–2,5 M шагов/с.
   Возрастающие времена остаются `O(C)` на шаг: каждое снятое сообщение —
   минимум, и фронтир узла пересобирается по всем его временам.
