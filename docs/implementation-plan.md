# План реализации Ariadne

> Этот ранний архитектурный черновик не является текущей спецификацией проекта.
> Актуальные проектные решения ведутся в [базе знаний OKF](../okf/index.md),
> начиная с [DSL описания графа](../okf/design/graph-dsl.md).

## Цель

Первый работающий срез Ariadne исполняет конечный timely dataflow-граф в одном
Erlang-процессе и следует базовой семантике из раздела 4.2 статьи
[*Timely Dataflow: A Model*](../okf/references/papers/timely-dataflow-a-model.md#42-semantics-specification).

Однопроцессный движок нужен не только как прототип. Он станет исполняемой
спецификацией, с которой можно сравнивать будущую многопроцессную реализацию.

## Граница первого среза

В первую версию входят:

- статический ориентированный граф, включая циклы;
- входные, внутренние и выходные рёбра;
- отдельная FIFO-очередь `Q(e)` для каждого ребра;
- локальное состояние и множество запросов уведомлений каждого узла;
- сообщения с виртуальным временем;
- частичный порядок времён;
- обработка сообщений и допустимых уведомлений;
- консервативное отслеживание прогресса на основе `could-result-in`;
- детерминированная стратегия выбора следующего допустимого перехода;
- пакетный режим: входы заданы до запуска и считаются закрытыми.

Пока не входят:

- распределение узлов между процессами или BEAM-нодами;
- динамическое изменение графа;
- неограниченные потоковые входы и входные фронтиры;
- сохранение состояния, восстановление после сбоев и exactly-once delivery;
- backpressure и управление памятью;
- оптимизации с переупорядочиванием сообщений.

Пакетный режим — осознанное начальное ограничение. Если вход остаётся открытым и
может позднее принять сообщение с любым временем, движок не может корректно
утверждать, что время завершено. Для потокового API позже потребуется явный
входной frontier или операция закрытия диапазона времён.

## Соответствие модели и реализации

| Модель статьи | Представление в первом срезе |
| --- | --- |
| Узлы `P` | определения операторов и их локальные состояния |
| Рёбра `I`, `E`, `O` | определения рёбер и FIFO-очереди |
| Сообщение `m in M` | значение с обязательным виртуальным временем |
| `Initial(p)` | инициализация оператора: состояние и первые запросы уведомлений |
| `g1(p)` | callback оператора для сообщения или уведомления |
| `NotRequests(p)` | множество времён в состоянии движка |
| pointstamp `(x, t)` | пара из местоположения графа и времени |
| `could-result-in` | консервативные временные сводки операторов плюс достижимость в графе |
| `Clock` | логическая проверка достижимости от активных pointstamp; замыкание не материализуется целиком |
| `Mess` и `Not` | атомарные переходы чистого ядра |
| `Inp` и `Outp` | загрузка закрытых входов перед запуском и чтение результатов после него |

Точное отношение `could-result-in` нельзя в общем случае вывести из
произвольного Erlang-кода оператора. Поэтому оператор обязан объявить
консервативную временную сводку: какие времена он может породить на каждом
выходе в ответ на входное время. Ошибка в сторону лишней достижимости задержит
уведомление; пропущенная достижимость может сделать результат некорректным.

## Предлагаемая структура

Чистое ядро не зависит от OTP и принимает все решения через явное состояние:

```text
ariadne_graph        проверка и нормализация описания графа
ariadne_operator     behaviour и контракт аналога g1
ariadne_time         behaviour частичного порядка времён
ariadne_progress     pointstamp, could-result-in и допустимость уведомлений
ariadne_engine       состояние графа и один атомарный переход
ariadne_runtime      один gen_server, владеющий одним ariadne_engine
```

`ariadne_runtime` — единственный процесс исполнения графа на первом этапе.
Операторы не являются отдельными процессами и не обмениваются сообщениями через
mailbox: движок вызывает их как чистые callbacks и сам обновляет очереди.

Предварительный контракт оператора:

```erlang
init(Options) -> {ok, State, NotificationRequests}.

on_message(InputEdge, Message, State) ->
    {ok, NewState, NotificationRequests, Outputs}.

on_notify(Time, State) ->
    {ok, NewState, NotificationRequests, Outputs}.
```

`Outputs` содержит конечную последовательность сообщений для каждого выходного
ребра. Это непосредственно соответствует результату `g1`: новое локальное
состояние, новые запросы уведомлений и последовательности сообщений по выходам.
Точный Erlang-тип результата нужно закрепить до реализации API.

## Цикл исполнения

После валидации и инициализации графа процесс повторяет следующие действия:

1. Строит множество допустимых переходов: сообщения в головах входных и
   внутренних FIFO-очередей и запрошенные уведомления, разрешённые `Clock`.
2. Стабильный справедливый планировщик выбирает один переход.
3. Для сообщения движок удаляет его из очереди и вызывает `on_message/3`; для
   уведомления — удаляет запрос и вызывает `on_notify/2`.
4. Атомарно применяет новое локальное состояние, новые запросы уведомлений и
   выходные сообщения.
5. Завершает запуск, когда допустимых переходов больше нет.

Для воспроизводимости движок использует стабильный порядок идентификаторов
рёбер, узлов и времён. Это одна допустимая трасса недетерминированной модели, а
не дополнительное требование статьи.

Остановка при отсутствии допустимого действия имеет два разных исхода:

- успешный покой: входные и внутренние очереди пусты, а запросов уведомлений не
  осталось; данные в выходных очередях при этом являются результатом;
- зависший прогресс: входные и внутренние очереди пусты, но остались
  уведомления, которые `Clock` не разрешает выдать. Второй случай должен
  возвращаться как диагностируемая ошибка, а не маскироваться под успешное
  завершение.

## Этапы

### 1. Контракты и представление графа

- определить Erlang-типы идентификаторов, сообщений, времён, узлов и рёбер;
- определить behaviours оператора и временного домена;
- валидировать уникальность идентификаторов, концы рёбер и допустимые выходы;
- зафиксировать правила ошибок callbacks и отправки сообщений «в прошлое».

Результат: корректный граф можно создать и проинициализировать без исполнения.

### 2. Однопроцессное ядро сообщений

- реализовать чистое состояние движка;
- реализовать FIFO-очереди и переход `Mess`;
- реализовать загрузку закрытых входов и сбор выходов;
- добавить стабильный справедливый планировщик и предел числа шагов для
  диагностики незавершения.

Результат: линейные, разветвлённые и циклические графы без уведомлений
исполняются в одном процессе.

### 3. Прогресс и уведомления

- определить контракт временных сводок операторов;
- реализовать достижимость pointstamp и проверку членства в `Clock` без
  материализации бесконечного верхнего замыкания;
- реализовать переход `Not`;
- проверять необходимые ограничения, соответствующие Conditions 1 и 2 статьи,
  либо явно документировать доверенную часть контракта оператора.

Результат: уведомление выдаётся только тогда, когда сообщение соответствующего
времени больше не может появиться на входах узла.

### 4. OTP-оболочка и публичный API

- поместить одно состояние `ariadne_engine` внутрь одного `gen_server`;
- определить API запуска, ожидания покоя, чтения выходов и остановки;
- возвращать структурированные ошибки валидации, callback и зависшего прогресса;
- добавить телеметрию шагов без изменения семантики ядра.

Результат: один граф полностью исполняется одним Erlang-процессом под
supervisor.

### 5. Многопроцессное исполнение

- назначить владение узлами и очередями отдельным процессам;
- заменить атомарное локальное обновление протоколом доставки и учёта progress;
- сохранить FIFO для каждого логического ребра независимо от числа отправителей;
- добавить распределённый подсчёт активных pointstamp/frontier;
- прогонять одинаковые сценарии через однопроцессный и многопроцессный движки,
  сравнивать наблюдаемые выходы и проверять допустимость каждого уведомления;
  порядок независимых событий при этом может различаться.

Результат: размещение частей графа меняет производительность, но не смысл
вычисления.

## Критерии готовности первого рубежа

- весь runtime одного графа имеет ровно один процесс-владелец;
- линейный граф сохраняет данные, времена и FIFO-порядок;
- fan-out создаёт независимые последовательности на каждом выходном ребре;
- stateful-оператор корректно накапливает состояние между событиями;
- ограниченный циклический граф с возрастающим временем завершается на конечном
  входе;
- уведомление не приходит, пока существует причинно достижимая работа;
- одинаковый граф и вход дают одинаковую трассу и результат;
- нарушение контракта времени и незавершающийся граф дают явную диагностику;
- модульные тесты сопоставляют переходы движка с `InitProp`, `Mess` и `Not` из
  статьи.

## Ближайшее решение

Перед написанием движка нужно утвердить минимальный Erlang API описания графа и
форму временной сводки оператора. Именно эти два контракта сильнее всего влияют
на возможность позже разнести граф по процессам без переписывания операторов.
