# Локальный runtime Ariadne

`ari_local_runtime` исполняет граф целиком внутри одного Erlang-процесса. Этот
процесс владеет состояниями всех узлов, очередями всех рёбер, запросами
уведомлений и состоянием прогресса. Узлы процессами не являются: runtime
вызывает их callbacks и сам обновляет очереди.

Собственных процессов runtime не создаёт и в дереве супервизоров не нуждается:
прогон идёт по месту вызова, и всё перечисленное состояние принадлежит
вызывающему процессу. `ari_local_runtime` остаётся набором функций,
`ariadne_sup` его не запускает.

Позднее рядом могут появиться другие модели исполнения, например
`ari_concurrent_runtime`, распределяющий узлы и рёбра по процессам. Этот
документ описывает только локальную модель. Вопрос о том, служит ли она
эталоном для остальных и в каком именно смысле, будет рассмотрен после
реализации локального runtime.

## Вход

Runtime принимает плоский `#graph{nodes, edges}`, собранный
[DSL описания графа](graph-dsl.md). Циклы к этому моменту раскрыты: `#loop{}` в
графе отсутствует, границы циклов размечены как `#ingress{}` и `#egress{}`,
обратные рёбра — как `#feedback{}`, и каждое специальное ребро связано с именем
своего цикла. Структурные проверки — уникальность имён, существование узлов на
концах рёбер, ацикличность после исключения feedback-рёбер — выполнены до
runtime.

Входные и выходные полурёбра остаются в графе как рёбра с `from = undefined` и
`to = undefined`. Первые являются точками загрузки входа, вторые — точками сбора
результата.

## Сборка

Перед первым вызовом `init/1` runtime проверяет то, что `ari_graph` сознательно
оставляет ему:

- модуль каждого узла доступен и экспортирует функции
  [контракта узла](node.md);
- каждый слот, названный концом ребра, объявлен в `Module:input()` или
  `Module:output()` соответствующего узла.

Затем сборка переводит `#graph{}` в форму, удобную для исполнения. `#graph{}`
хранит рёбра списком, и каждое ребро знает свои концы. Шаг спрашивает граф в
обратную сторону: узел вернул `{OutputSlot, Message, Time}`, и нужны рёбра
этого слота. Сборка отвечает на такой вопрос одним обращением по ключу.

```erlang
-record(program, {
    nodes     :: #{name() => #pnode{}},
    edges     :: #{name() => #pedge{}},
    edge_order :: [name()],  % стабильный порядок рёбер
    node_order :: [name()],  % стабильный порядок узлов
    inputs    :: [name()],   % входные полурёбра
    outputs   :: [name()],   % выходные полурёбра
    summaries :: #{{name(), name()} => [summary()]}  % сводки непустых путей
}).

-record(pnode, {
    module  :: module(),
    args    :: term(),
    depth   :: non_neg_integer(),      % глубина времени узла
    outputs :: #{slot() => [name()]}   % куда уходит выход слота
}).
```

`#pnode.depth` равна числу охватывающих циклов из `#node.context`, который
`ari_graph` заполняет при раскрытии циклов. По рёбрам глубину не восстановить:
цикл без полурёбер допустим.

`#pnode.outputs` содержит ключ для каждого объявленного выходного слота.
Слот без рёбер хранится с пустым списком: выход в такой слот никуда не
доставляется, а выход в слот, отсутствующий среди ключей, является ошибкой
маршрутизации. Входные слоты проверяются при сборке и отдельного индекса
не получают: сообщение приходит с ребра, а ребро знает свой слот.

```erlang

-record(pedge, {
    kind :: message | ingress | egress | feedback,
    loop :: name() | undefined,
    from :: {name(), slot()} | undefined,
    to   :: {name(), slot()} | undefined
}).
```

Ключами служат имена узлов и рёбер из DSL. Имя читается в диагностическом
сообщении без обратного перевода.

Четыре вида рёбер сводятся к одной записи с полем `kind`. Различие между ними
сжимается до выбора преобразования времени, и цикл шага перестаёт разбирать
записи DSL.

`#program.edge_order` и `#program.node_order` фиксируют стабильные порядки
рёбер и узлов: имена сортируются по порядку Erlang-термов при сборке.
Списки рёбер в `#pnode.outputs` следуют `edge_order`. Воспроизводимость трассы
не опирается на порядок обхода map или порядок объявлений в DSL.

`#program.summaries` описан в разделе
[«Достижимость и could-result-in»](#достижимость-и-could-result-in).

`#program{}` неизменна весь прогон, и по одной программе можно пройти много
прогонов. Начальные состояния узлов принадлежат прогону, поэтому `init(Args)`
каждого узла вызывается в `new/2` вместе с наполнением входных очередей. Оттуда
берутся начальное состояние и начальные запросы уведомлений.

Сообщений `init/1` не порождает: по начальному условию
[раздела 4.2 статьи](../references/papers/timely-dataflow-a-model.md#42-semantics-specification)
внутренние и выходные рёбра при старте пусты, `Q(e) = ∅`, а сообщения лежат
только на входных полурёбрах.

Начальные запросы уведомлений правилу времени узла не подчиняются: входного
времени при инициализации нет, сравнивать не с чем. `Clock` определён через
`NotRequests(p)` наравне с сообщениями в очередях, поэтому возможные
последствия начальных запросов учтены с первого шага.

Проверяется только форма времени: `ari_vtime:valid(Time, Depth)` требует
целую эпоху и ровно `Depth` неотрицательных координат, где `Depth` —
глубина контекста узла из `#pnode.depth`. Запрос чужой глубины уронил бы
`ari_vtime:le/2` внутри планировщика при первой проверке допустимости, а
ошибка узла не должна выглядеть ошибкой планировщика. Той же проверке
подлежат времена входных сообщений относительно узла-получателя.

## Состояние

Меняющаяся часть прогона:

```erlang
-record(execution, {
    program    :: #program{},
    states     :: #{name() => term()},
    queues     :: #{name() => queue:queue({term(), ari_vtime:t()})},
    counts     :: #{name() => #{ari_vtime:t() => pos_integer()}},
    notify     :: #{name() => ordsets:ordset(ari_vtime:t())},
    ready      :: queue:queue(item()),
    scheduled  :: #{{name(), ari_vtime:t()} => true},
    messages   :: ari_progress:frontier(),
    requests   :: ari_progress:frontier(),
    stale      :: all | #{{message | request, name()} => true},
    blockers   :: #{ari_progress:blocker() => [{name(), ari_vtime:t()}]},
    candidates :: [{name(), ari_vtime:t()}],
    steps      :: non_neg_integer(),
    violations :: [violation()]
}).

-type item() :: {edge, name()} | {notify, name(), ari_vtime:t()}.
```

`states` хранит состояние каждого узла, `violations` — нарушения, накопленные по
ходу прогона; их описывает раздел «API».

Очередь заводится на каждое ребро, включая входные и выходные полурёбра.

`notify` хранит множество времён: повторный запрос того же времени ничего не
добавляет. Уведомление не несёт ничего кроме времени, поэтому два одинаковых
уведомления неразличимы. Узел вправе запрашивать время на каждом сообщении, не
помня прежних запросов.

`counts` считает живые сообщения по pointstamp'ам: счётчик времени `T` у
узла `X` покрывает все сообщения этого времени, лежащие на входящих рёбрах
узла. Счётчики сгруппированы по узлу, чтобы фронтир одного узла
пересобирался по его временам, не обходя чужие. Инкремент при укладке
сообщения в очередь, декремент при снятии, счётчик с нулём удаляется, узел
без счётчиков ключа не имеет. Запросы уведомлений в `counts` не входят и
живут в `notify`.

`ready` содержит готовые переходы: `{edge, Name}` для рёбер, готовых отдать
сообщение, и `{notify, X, T}` для допустимых уведомлений. Метки различают
виды переходов независимо от формы имени ребра.

Ребро попадает в хвост `ready`, когда его очередь становится непустой.
После обслуживания оно возвращается в хвост, если сообщения остались.
Отдельное множество поставленных рёбер не требуется: саморёбра запрещены,
поэтому callback получателя не может пополнить обслуживаемое ребро на том же
шаге. Между шагами каждое непустое ребро с получателем представлено в `ready`
ровно один раз.

`scheduled` содержит пары `{X, T}` уведомлений, уже поставленных в `ready`.
Допустимый запрос добавляется в хвост только при отсутствии такой пары;
одновременно в `scheduled` записывается `true`. Запрос остаётся в `notify`
и учитывается при проверке прогресса до исполнения. Между шагами каждая пара
из `scheduled` соответствует ровно одному элементу `ready` и запросу из
`notify`. Повторная проверка или повторный запрос ожидающего времени дубликат
в `ready` не создают.

`messages` и `requests` — фронтиры `counts` и `notify` из раздела «Проверка
допустимости уведомления», поддерживаемые по ходу шага. `stale` отмечает
узлы, чей фронтир пересобирается перед следующей проверкой. `blockers`
хранит свидетеля каждого заблокированного запроса: время фронтира, которое
его блокирует. `candidates` — запросы, ожидающие проверки: новые и
освобождённые исчезнувшим свидетелем. Между шагами каждый запрос из
`notify` без отметки в `scheduled` ждёт ровно в одном месте: в
`candidates` или в списке одного свидетеля.

Выходные полурёбра в `ready` не попадают никогда: у них `to = undefined`, и
доставлять их сообщения некому. Содержимое их очередей является результатом
прогона.

Первая версия работает в пакетном режиме: входные очереди наполняются до
запуска и считаются закрытыми, выходные очереди накапливают результат и
читаются после остановки.

## Инициализация готовых переходов

`new/2` сначала вызывает все `init/1` в `node_order`, загружает входные
сообщения и полностью формирует `states`, `queues`, `counts` и `notify`.
До этого момента допустимость уведомлений не проверяется: ещё не учтённый
вход или запрос другого узла мог бы их заблокировать.

Затем runtime наполняет пустую `ready` непустыми входными рёбрами в
`edge_order`. После этого он проверяет все запросы и добавляет допустимые
уведомления с отметками в изначально пустом `scheduled`. Уведомления идут
после рёбер, по `node_order`, а внутри узла — по порядку Erlang-термов времени.
Этот порядок определяет очередность исполнения; допустимость определяется
отдельно через `ari_vtime:le/2` и сводки путей.

При пустом входе начальные запросы также проверяются и могут запустить
вычисление. Инициализация не увеличивает `steps`.

## Шаг

Один шаг является одним атомарным переходом состояния графа и соответствует
`Mess` или `Not` из
[раздела 4.2 статьи](../references/papers/timely-dataflow-a-model.md#42-semantics-specification):

1. runtime берёт с головы `ready` очередной переход: `{edge, Name}` либо
   `{notify, X, T}`;
2. для ребра runtime снимает сообщение с головы его очереди и вызывает
   `handle_message(InputSlot, Message, Time, State)` узла из `#pedge.to`; для
   уведомления `{notify, X, T}` удаляет пару из `scheduled`, снимает запрос
   из `notify` и вызывает `handle_notification(T, State)`;
3. runtime строит новое состояние исполнения из результата callback за один
   проход, без предварительной валидации содержимого сообщений;
4. каждое выходное `{OutputSlot, Message, Time}` копируется в очередь каждого
   ребра этого слота из `#pnode.outputs`, время преобразуется по `#pedge.kind`,
   и ребро с получателем попадает в хвост `ready`, если его очередь была пуста;
5. при успешном применении всего результата runtime принимает построенное
   состояние; при исключении отбрасывает результат по правилу `invalid_result`
   ниже. Обработанное ребро возвращается в хвост `ready`, если его очередь
   ещё не пуста;
6. если шаг удалил ключ из `counts` или снял запрос из `notify`, runtime
   проверяет кандидатов — новые запросы и запросы, чей свидетель исчез, —
   и ставит допустимые в хвост `ready`, одновременно добавляя отметки в
   `scheduled`; заблокированный кандидат получает свидетеля;
7. шаги повторяются, пока существует допустимый переход.

Все пункты шага завершаются до возврата управления вызывающему; промежуточное
состояние не наблюдается. Если `handle_notification/2` снова запрашивает `T`,
это новый ожидающий запрос: прежний уже снят вместе с отметкой `scheduled`.
После применения результата новый запрос проверяется и, если допустим,
становится в хвост `ready`. При исключении callback или отбрасывании его
результата снятые запрос и отметка также не восстанавливаются.

Применение результата использует обычные функциональные обновления Erlang:
разбор, сравнение времён и маршрутизация выполняются за один проход, без
предварительного прохода валидации и полного копирования состояния. До успеха
сохраняется исходное состояние исполнения после потребления события. Исключения
перехватываются отдельно вокруг callback и применения его результата;
ошибки самого планировщика не превращаются в нарушения узла.

Пункты 1 и 5 задают обход рёбер по кругу. Ребро, готовое отдать сообщение,
дождётся своей очереди за конечное число шагов. Тот же обход задаёт порядок
между несколькими рёбрами, ведущими в один входной слот: FIFO гарантируется на
каждом ребре, а между головами разных рёбер выбирает `ready`.

Пункт 6 выполняется после того, как шаг применён целиком. Проверять сразу после
декремента нельзя: выходные сообщения укладываются позже, и в промежутке живых
pointstamp'ов меньше, чем на самом деле. Узел `X` снимает сообщение времени `5`,
ключ `{X, 5}` исчезает, запрос `(Y, 5)` выглядит допустимым, а дальше на том же
шаге `X` выдаёт в `Y` выход времени `5`, и запрос снова запрещён.

Удаление в пункте 6 учитывается как событие шага: проверка нужна, даже если
последующее применение результата восстановило тот же ключ или запрос.
Это не сравнение наборов ключей до и после перехода.

Для уже ожидающих запросов допустимость приобретается только при исчезновении
блокирующего источника работы. Проверка перебирает поэтому только
кандидатов: каждый заблокированный запрос помнит свидетеля —
время фронтира, на котором проверка остановилась, — и возвращается в
кандидаты, когда свидетель исчезает из `counts` или `notify`. Остальные
запросы по-прежнему блокирует их свидетель, и перепроверять их незачем.
Меньшее время, вытеснившее свидетеля из фронтира, наследует его
свидетельство: оно блокирует всё, что блокировал вытесненный. Полный перебор
ожидающих запросов даёт тот же набор допустимых.

Новый запрос после обработки сообщения также не требует отдельной проверки,
если ключ не исчез: в том же узле осталось сообщение входного времени, а
запрошенное время по правилу узла не меньше входного. Это сообщение блокирует
новый запрос прямым сравнением. Потребление уведомления всегда запускает
проверку, в том числе для запросов, созданных его callback.

Порядок среди уведомлений, добавляемых на одном шаге, задаётся позицией узла
в `#program.node_order`, затем порядком Erlang-термов времени.

При закрытом входе и соблюдении временного правила допустимость устойчива:
новая работа достижима из уже учтённой. Поэтому ожидание в хвосте `ready`
не портит допустимость, и при извлечении уведомления повторная проверка
не требуется.

### Проверочные сценарии планирования

- Пустой вход и допустимый запрос из `init/1`: первый переход — уведомление.
- Начальный запрос блокируется входом или запросом другого узла: он не
  ставится в `ready` до исчезновения блокировки, независимо от порядка `init`.
- Несколько пересчётов до исполнения уведомления: в `ready` остаётся ровно
  один его элемент, в `scheduled` — одна отметка.
- Повторный запрос ожидающего времени не меняет его место в `ready`.
- Повторный запрос из собственного callback проходит новую проверку и
  ставится в хвост, если допустим; он не исполняется рекурсивно внутри callback.
- Исчезновение и восстановление запроса на одном шаге не пропускает проверку.
- Несколько сообщений на ребре обрабатываются по FIFO, ребро присутствует
  в `ready` однократно, а выходные полурёбра туда не попадают.
- Для одинаковых результатов callbacks разные бюджеты `advance/2` разбивают
  одну и ту же последовательность переходов, не меняя её порядок.

## Правило времени узла

Runtime решает, допустимо ли уведомление о времени `t` в узле, по тому, способно
ли живущее в графе сообщение или запрос уведомления породить сообщение с
временем `t' =< t` на входе этого узла. Ответ складывается из поведения времени на рёбрах и внутри узла.

Поведение на рёбрах выводится из графа. Поведение внутри узла из произвольного
Erlang-кода вывести нельзя, поэтому его задаёт общее правило: узел выдаёт время
не раньше входного. Для каждого выходного сообщения истинно

```erlang
ari_vtime:le(InputTime, OutputTime)
```

где `InputTime` — время обрабатываемого сообщения либо время уведомления. Для
частичного порядка это строже словесного «не раньше»: несравнимое время тоже
запрещено.

Тому же правилу подчиняется запрос уведомления: узел вправе запросить время
`RequestedTime`, когда истинно `ari_vtime:le(InputTime, RequestedTime)`. Это
соответствует Condition 1 статьи: новые запросы не направлены в прошлое.
Обработчик уведомления может повторно запросить то же время. Такой запрос
сам по себе не означает возможности нового входного сообщения этого времени:
она проверяется отдельно по непустым путям графа.

Правило избавляет [контракт узла](node.md) от объявления временной сводки:
сводка пути считается по графу целиком.

Проверка всегда выполнима. Преобразования цикла живут на рёбрах, поэтому вход и
выход узла лежат в одном временном контексте и имеют одинаковую глубину — ровно
то, что требует `ari_vtime:le/2`.

`ari_graph` проверяет ацикличность каждого контекста со свёрнутыми вложенными
циклами после исключения собственных feedback-рёбер. Поэтому обход на уровне
контекста проходит через его `#feedback{}`, увеличивающий координату этого
цикла. Время сравнивается по эпохе и лексикографически по счётчикам от
внешнего цикла к внутреннему. На обратном пути счётчик контекста повторения
растёт, а сброс более внутренних счётчиков не отменяет этот рост. Поэтому
возврат из узла на его входящее ребро удовлетворяет `t =< t'`, как требует
Condition 2 из
[раздела 3.2 статьи](../references/papers/timely-dataflow-a-model.md#32-on-sending-notification-requests-and-messages-into-the-past).

### Нарушение правила

Сообщение, нарушившее правило, отбрасывается, и runtime сообщает об ошибке.
Доставка такого сообщения сломала бы уже выданную гарантию: уведомление о
времени `t` могло сработать раньше, и узел-получатель считает это время
завершённым.

Запрос уведомления, нарушивший правило, отбрасывается так же. Его обработчик
мог бы породить сообщения вне учтённого будущего текущего перехода и нарушить
уже выданные гарантии завершения на достижимых входах.

Каждое время выходного сообщения и запроса сначала проверяется на форму:
`ari_vtime:valid(ReturnedTime, Depth)` с глубиной узла. Время не той формы
поднимает исключение `{invalid_time, ReturnedTime}` и отбрасывает весь
результат как `invalid_result`: `le/2` не проверяет структуру, и такое время
ушло бы дальше по графу. Затем время проверяется существующим
`ari_vtime:le(InputTime, ReturnedTime)`. Если результат — `false`, только
соответствующее сообщение или запрос отбрасывается с `time_rule`; новое
состояние узла и остальные результаты применяются.

Если разбор или применение результата callback вызывает исключение, весь
результат отбрасывается с `invalid_result`. Неизвестный выходной слот
обрабатывается так же: ошибка возникает при маршрутизации. Входное событие остаётся
потреблённым, прежнее состояние узла сохраняется; новые выходы, запросы и
промежуточные изменения очередей и счётчиков не сохраняются. Накопленные при
этой попытке записи `time_rule` также отбрасываются: вместо них добавляется
одно нарушение `invalid_result` для всего результата.

Непойманное исключение внутри самого callback записывается как `crash`.
Прежнее состояние узла сохраняется, а входное событие остаётся потреблённым.
Содержимое `Message` runtime не проверяет: например, `function_clause` в
обработчике пользовательских данных становится обычным `crash`.

Шаг остаётся чистым и возвращает нарушение вызывающему; писать ли его в лог,
решает вызывающий. Список `#execution.violations` доводит нарушения до
результата прогона, минуя лог.

## Преобразование времени на рёбрах

Узел работает во времени своего контекста и преобразований цикла не выполняет.
Их выполняет runtime в момент переноса сообщения через ребро:

| `#pedge.kind` | Ребро DSL | Преобразование времени |
| --- | --- | --- |
| `message` | `#edge{}` | без изменения |
| `ingress` | `#ingress{}` | `ari_vtime:ingress/1` |
| `feedback` | `#feedback{}` | `ari_vtime:feedback/1` |
| `egress` | `#egress{}` | `ari_vtime:egress/1` |

Преобразование выполняется при помещении сообщения в очередь ребра. Отсюда
инвариант: время сообщения в очереди выражено во временном контексте
получателя, и прогресс читает очереди в координатах узла-получателя без
пересчёта.

Глубина стека координат [времени](time.md) определяется местом сообщения в
графе, и внутри одного цикла все времена имеют одинаковую глубину.

## Достижимость и `could-result-in`

Допустимость уведомления сводится к вопросу: способно ли сообщение или запрос
уведомления в узле `X1` со временем `T1` породить сообщение с временем
`T' =< T2` на входе узла `X2`. Для переноса между узлами ответ даёт сводка
пути — композиция преобразований времени вдоль рёбер.

Сообщения из `counts` сгруппированы по узлу-получателю и времени уже после
преобразования на входящем ребре. Запросы из `notify` принадлежат узлам.
Вид источника работы сохраняет значение: сообщение уже находится на входе
своего узла, а запрос может породить новый вход только через путь по рёбрам.
Выходные полурёбра не имеют получателя и не могут породить дальнейшую работу.

`#program.summaries` хранит только непустые пути, содержащие хотя бы одно ребро.
Для пары `{X, X}` это реальные обратные пути. Пустой путь в таблицу не
добавляется: его тождественная сводка вытеснила бы нужные сводки обратных путей
при минимизации. При этом непустой путь вправе иметь тождественное
преобразование времени, например обычное ребро между разными узлами.

Сводки статичны вслед за графом и вычисляются один раз при сборке. Проверка
внутри шага становится поиском по ключу и несколькими сравнениями вместо обхода
графа.

### Нормальная форма сводки

Сводка меняет глубину времени и потому является функцией, а не сдвигом. Любая
композиция рёбер приводится к тройке «снять, увеличить, добавить». Сводка
разбирает внутренности opaque `ari_vtime:t()`, поэтому живёт в `ari_vtime`
как opaque `summary()`:

```erlang
-record(summary, {
    pop  = 0  :: non_neg_integer(),   % снятые координаты циклов
    bump = 0  :: non_neg_integer(),   % прибавка к внутренней уцелевшей координате
    push = [] :: [non_neg_integer()]  % добавленные координаты, внутренняя первой
}).

transfer(#summary{pop = D, bump = K, push = P}, {Epoch, Iterations}) ->
    case lists:nthtail(D, Iterations) of
        [] -> {Epoch, P};
        [I | Rest] -> {Epoch, P ++ [I + K | Rest]}
    end.
```

`ari_vtime:summary/1` даёт сводку ребра по виду, `summary/3` собирает сводку
из компонентов, `transfer/2` переносит время по пути, `compose/2` соединяет
два пути, `dominates/2` сравнивает сводки одной формы. Имя `apply` занято
автоимпортом `erlang:apply/2`.

Базовые случаи, по одному на вид ребра:

| `#pedge.kind` | Сводка |
| --- | --- |
| `message` | `{0, 0, []}` |
| `ingress` | `{0, 0, [0]}` |
| `feedback` | `{0, 1, []}` |
| `egress` | `{1, 0, []}` |

Время является стеком координат, и рёбра дают на нём три операции: положить
ноль, снять, увеличить голову. Отсюда два ограничения, сжимающие произвольную
композицию до тройки.

Уцелевшая координата увеличивается ровно одна, самая внутренняя. Чтобы добраться
до более внешней координаты, нужно снять внутреннюю, а снятая координата в
результат не попадёт. Вектор прибавок поэтому не нужен, хватает числа.

Добавленные координаты независимы. Каждая пришла нулём и росла, пока была
головой, до следующего добавления. `push` поэтому является списком констант.

Пример для графа с источником `S`, циклом из узлов `A` и `B` и приёмником `K` за
`egress`:

| Путь | Сводка | Действие |
| --- | --- | --- |
| `S -> A` | `{0, 0, [0]}` | `{5, []}` → `{5, [0]}` |
| `A -> A`, один оборот | `{0, 1, []}` | `{5, [0]}` → `{5, [1]}` |
| `A -> A`, два оборота | `{0, 2, []}` | доминируется предыдущей |
| `A -> K` | `{1, 0, []}` | `{5, [3]}` → `{5, []}` |
| `S -> K` | `{0, 0, []}` | сколько бы оборотов ни прошло |

Последние две строки показывают, зачем нужна нормальная форма. Список видов
рёбер вдоль пути `S -> K` растёт с числом оборотов и бесконечен, а нормальная
форма у всех этих путей одна.

### Композиция сводок

`compose(First, Second)` описывает путь `First`, продолженный путём `Second`.
После `First` стек имеет вид `P1 ++ [I + K1 | Rest]`, и `Second` снимает с
него `D2` координат. Исход зависит от `D2` относительно `L = length(P1)`:

| Случай | Результат |
| --- | --- |
| `D2 < L` | `{D1, K1, P2 ++ bump_head(drop(D2, P1), K2)}` |
| `D2 =:= L` | `{D1, K1 + K2, P2}` |
| `D2 > L` | `{D1 + D2 - L, K2, P2}` |

В первом случае `Second` снимает только добавленное `First`, уцелевшая
координата и `K1` сохраняются, а `K2` увеличивает голову остатка `P1`. Во
втором `P1` исчерпан ровно, и `K2` увеличивает ту же уцелевшую координату,
что и `K1`. В третьем снята и уцелевшая координата `First` вместе с `K1`;
из исходного стека снято `D1`, затем ещё `D2 - L` координат. Композиция
проверяется сравнением с последовательным применением преобразований рёбер
на всех путях ограниченной длины.

### Проверка допустимости уведомления

Сводка приводит время источника в контекст назначения, после чего сравниваются
времена одной глубины. Проверка непустых путей имеет вид:

```erlang
path_blocks(Y, U, X, T, Summaries) ->
    lists:any(fun(S) -> ari_vtime:le(ari_vtime:transfer(S, U), T) end,
              maps:get({Y, X}, Summaries, [])).
```

Уведомление `(X, T)` допустимо, если ни один источник работы не блокирует его:

```erlang
message_blocks(Y, U, X, T, Summaries) ->
    (Y =:= X andalso ari_vtime:le(U, T))
    orelse path_blocks(Y, U, X, T, Summaries).

request_blocks(Y, U, X, T, Summaries) ->
    path_blocks(Y, U, X, T, Summaries).
```

`message_blocks` проверяется для каждого времени `U` каждого узла `Y` из `counts`,
`request_blocks` — для каждого запроса `(Y, U)` из `notify`. Обе блокировки
монотонны по времени источника: преобразования рёбер монотонны, и если `U`
блокирует уведомление, его блокирует любое `U' =< U`. Поэтому достаточно
проверять фронтиры — минимальные времена каждого узла среди ключей `counts`
и среди запросов `notify`:

```erlang
-type frontier() :: #{name() => [ari_vtime:t()]}.

-spec message_frontier(counts()) -> frontier().
-spec request_frontier(requests()) -> frontier().
-spec admissible(name(), ari_vtime:t(), frontier(), frontier(), summaries())
    -> boolean().
```

Фронтир узла строится вставкой: каждое время сравнивается с оставленными,
доминируемое отбрасывается, доминирующее вытесняет. Это стоит `O(C * F)`
на узел при `F` оставленных и выигрывает при узком фронтире, обычном для
сообщений одного узла. Когда оставленных больше восьми, остаток копится как
есть, и в конце весь список сортируется `ari_vtime:sort/1` — по эпохе,
затем лексикографически по итерациям от внешнего цикла к внутреннему — и
проходится один раз: `le/2` есть произведение двух линейных порядков,
поэтому после сортировки время минимально ровно тогда, когда его итерации
строго меньше, чем у последнего оставленного. Порядок термов Erlang для
сортировки не годится: он сравнивает список итераций с головы, то есть с
внутреннего цикла. Оставленные до переключения минимумы достаточны:
отброшенные ими времена доминируются и после сортировки.

Все функции живут в модуле `ari_progress` и чисты: они получают фронтиры и
таблицу сводок явно, и таблица «Проверочные примеры» ниже проверяется
прямыми вызовами без сборки прогона. `blocker/5` возвращает первое
блокирующее время фронтира или `none`; `admissible/5` — его отрицание.
Сводки пары узлов берутся один раз на узел-источник, и источник без пути к
`X` и без прямого сравнения пропускается целиком.

Runtime хранит фронтиры в `#execution{}` и поддерживает их по ходу шага
с первого запроса в прогоне; до него `stale = all`, и первая проверка
строит фронтиры заново. Новый счётчик `counts` и новый запрос вставляются в
фронтир своего узла; исчезнувший счётчик или запрос помечает узел в `stale`,
и перед следующей проверкой фронтир узла пересобирается по его временам из
`counts` или `notify`. Сообщение снимается с ребра в порядке очереди и
минимальным обычно не является, поэтому фронтир сообщений помечается, только
если исчезнувшее время в него входило: исчезновение неминимального времени
минимумов не меняет. Запрос исполняется допустимым и обычно минимален, и его
снятие помечает узел без обхода фронтира. Время, выпавшее из фронтира при
пересборке, освобождает своих свидетельствуемых: их блокирует меньшее время,
всплывшее на его место, и проверка найдёт нового свидетеля. Пока кандидатов
нет, устаревшие фронтиры не пересобираются.

### Стоимость пересчёта

Обозначения: `C_X` — число времён узла `X` в `counts`, `R_X` — число его
запросов, `F_X` — ширина его фронтира, `D` — глубина времени, `K` — число
узлов-источников с непустым путём к проверяемому узлу.

- Сравнение времён `le/2` стоит `O(D)`; вставка времени в фронтир —
  `O(F_X)` сравнений.
- Пересборка фронтира узла — `O(C_X * min(F_X, 8))` сравнений при вставке
  и дополнительно `O(C_X * log C_X)` на сортировку при широком фронтире;
  для запросов то же с `R_X`.
- Проверка одного кандидата в узле `X` — `O(F_X)` прямых сравнений и
  `O(sum_Y F_Y * |S_YX|)` по источникам `Y` с путём к `X`, где `|S_YX|` —
  число минимальных сводок пары; источники без пути стоят `O(1)` на узел.
- За прогон запрос проверяется при появлении и по разу на каждого
  исчезнувшего свидетеля. Свидетель — минимум своего узла в момент
  проверки, и число перепроверок одного запроса ограничено числом таких
  исчезновений; при `K` источниках, блокирующих один запрос, оно доходит
  до `K`.
- Шаг без исчезновения минимума и без нового запроса пересчёта не
  вызывает; шаг, снявший минимум узла, оплачивает пересборку его фронтира.
  Возрастающие времена на одном узле дают поэтому `O(C_X)` на шаг,
  убывающие — `O(1)`.

Замеры приведены в
[замерах производительности](local-runtime-performance.md).

Прямое сравнение в `message_blocks` учитывает сообщение, уже находящееся на
входе `X`; обход графа ему для блокировки не нужен. Отсутствие ключа `{Y, X}`
означает отсутствие непустого пути, но не отменяет эту прямую проверку.

Запросы блокируют уведомление только через непустые пути к входу `X`.
Проверяемый запрос `(X, T)` участвует в переборе наравне с остальными.
Иерархическая проверка циклов и порядок времени гарантируют, что каждый
непустой обратный путь строго продвигает время, поэтому собственный запрос
не блокирует себя. Другой запрос того же узла может блокировать уведомление,
если его время после обратного пути оказывается `=< T`.

Это соответствует геометрии `Not1(p)` из
[раздела 4.2 статьи](../references/papers/timely-dataflow-a-model.md#42-semantics-specification):
проверяется наличие работы в `Clock` на входящих рёбрах. Сообщение уже лежит
на таком ребре, а запрос находится в узле и может повлиять на вход через
исходящие рёбра и дальнейший путь. Сводки дают консервативную аппроксимацию:
они допускают передачу по каждому выходу узла, даже если конкретный callback
не использует этот выход.

`transfer(S, U)` является нижней границей времени прибытия по соответствующему
пути. Преобразования рёбер монотонны, а узлы время не уменьшают, поэтому
фактическое время прибытия `T'` удовлетворяет `transfer(S, U) =< T'`.
Если `transfer(S, U) =< T` ложно, то `T' =< T` невозможно по транзитивности.

### Проверочные примеры

В каждой строке кроме проверяемого запроса имеется только указанный источник
работы. В примерах простого цикла путь `A -> B -> A` содержит одно
feedback-ребро и имеет сводку `{0, 1, []}`.

| Граф и источник работы | Проверяемое уведомление | Результат |
| --- | --- | --- |
| Ациклический `A`, сообщение `(A, {5, []})` | `(A, {5, []})` | запрещено прямой проверкой сообщения |
| Ациклический `A`, запрос `(A, {5, []})` | `(A, {6, []})` | допустимо: обратного пути нет |
| Простой цикл, запрос `(A, {5, [0]})` | `(A, {5, [1]})` | запрещено: обратный путь даёт `{5, [1]}` |
| Простой цикл, только сам проверяемый запрос | `(A, {5, [0]})` | допустимо: обратный путь даёт `{5, [1]}` |
| Простой цикл, сообщение `(A, {5, [3]})` | `(A, {5, [2]})` | допустимо: прямое сравнение и обратный путь не блокируют |
| `A -> K` через egress, сообщение `(A, {5, [3]})` | `(K, {5, []})` | запрещено: сводка `{1, 0, []}` даёт `{5, []}` |
| Возврат во внутренний цикл через внешний feedback, запрос `(A, {5, [3, 0]})` | `(A, {5, [0, 1]})` | запрещено: сводка `{1, 1, [0]}` даёт `{5, [0, 1]}` |

В последнем примере путь состоит из выхода из внутреннего цикла, feedback
внешнего цикла и повторного входа во внутренний. Рост внешнего счётчика
допускает сброс внутреннего; собственный запрос `(A, {5, [0, 1]})` при этом
не блокирует себя, поскольку его следующий возврат даст `{5, [0, 2]}`.

### Минимальные сводки

Между двумя узлами бывает несколько путей, и `could-result-in` истинно при
существовании хотя бы одной подходящей сводки. Ключ `{X1, X2}` хранит антицепь
минимальных сводок непустых путей. Начальное наполнение таблицы берётся из
рёбер с определёнными источником и получателем. Каждый следующий кандидат
получается продолжением уже найденного пути ещё одним ребром; пустые пути
не добавляются ни при инициализации, ни при вычислении неподвижной точки.

Сводки одной формы, с равными `pop` и равной длиной `push`, сравниваются
покомпонентно по `bump` и `push`. Доминируемая сводка даёт большее время, а
большее время не окажется `=< T`, когда меньшее уже не оказалось. Проверять
оставшиеся сводки поэтому достаточно. Покомпонентная проверка доминирования
консервативна относительно лексикографического порядка итераций: она может
оставить лишнюю сводку, но не удалит необходимую.

Сводки разной формы остаются в антицепи обе. Лишняя сводка стоит лишней
проверки, и хранить лишнее безопасно. Антицепь хранится отсортированным
списком, чтобы две одинаковые таблицы совпадали структурно.

Тем же свойством обрывается вычисление при сборке. Путь вправе обойти цикл любое
число раз, каждый проход через `#feedback{}` увеличивает координату цикла, и
лишние обходы дают доминируемые сводки. Вычисление является неподвижной точкой:
композиция вдоль ребра и отбрасывание доминируемых.

Неподвижная точка считается списком необработанных сводок. Список начинается
со сводок рёбер; сводка, изменившая таблицу, продолжается каждым ребром из
своего конца, и продолжения встают в список. Сводка, не изменившая таблицу,
доминируется и продолжений не даёт. Вытеснение уже продолженной сводки
результат не меняет: композиция сохраняет доминирование, и продолжения
вытесненной доминируются продолжениями вытеснившей. Полный перебор таблицы
на каждом круге даёт ту же таблицу, но на цепочке из `N` узлов стоит
`O(N^4)` против `O(N^2)` у списка; замеры приведены в
[замерах производительности](local-runtime-performance.md).

Новой операции сравнения `ari_vtime` не требует. После приведения времени обе
стороны `le/2` имеют одинаковую глубину.

## Остановка

Прогон останавливается в покое: `ready` пуста и запросов уведомлений не
осталось. Содержимое выходных очередей является результатом прогона.

Runtime проверяет только пустоту `ready`; отсутствие запросов при этом
выводится, а не проверяется, и `inspect/1` позволяет убедиться в нём в тестах.
Пока запросы остаются, переход существует. Пустая `ready` означает отсутствие
живых сообщений, поэтому запретить уведомление могут только другие запросы.
Цикл зависимостей между запросами означал бы замкнутый путь, который возвращает
время не большим исходного. Это невозможно: обратный путь строго продвигает
время. Запросов конечное число, поэтому существует запрос без блокирующих
предшественников, допустимый для постановки в `ready`.

Покоя может не быть вовсе. Узел, выдающий сообщение в обратное ребро на каждое
входящее, крутит цикл бесконечно, и `ready` не пустеет. Структура графа этого не
ловит: проверка ацикличности ограничивает повторы времени, а не число оборотов.
Прогон идёт в процессе вызывающего и своего Pid не имеет, поэтому работа
отмеряется бюджетом шагов: вызывающий получает управление обратно вместе с
состоянием прогона и решает, продолжать ли. Форма описана в разделе «API».

## API

Прогон состоит из трёх вызовов. Сборка выполняется один раз на граф, прогонов по
собранной программе может быть много.

```erlang
-spec compile(#graph{}) -> {ok, program()} | {error, compile_error()}.
-spec new(program(), inputs()) -> {ok, execution()} | {error, new_error()}.
-spec advance(execution(), pos_integer() | infinity) ->
    {done | more, execution()}.

-spec outputs(execution()) -> outputs().
-spec violations(execution()) -> [violation()].
-spec steps(execution()) -> non_neg_integer().
-spec inspect(program() | execution()) -> map().

-opaque program() :: #program{}.
-opaque execution() :: #execution{}.

-type compile_error() ::
    {unknown_module, name(), module()}
  | {missing_callback, name(), module(), {atom(), arity()}}
  | {unknown_input_slot, name(), name(), slot()}
  | {unknown_output_slot, name(), name(), slot()}.
-type new_error() ::
    {unknown_input, name()}
  | {duplicate_input, name()}
  | {invalid_input, name(), term()}
  | {init_crashed, name(), exception()}
  | {invalid_notification, name(), term()}.

-type inputs()  :: [{name(), [{term(), ari_vtime:t()}]}].
-type outputs() :: #{name() => [{term(), ari_vtime:t()}]}.
-type violation() ::
    {time_rule, name(), message | notification, ari_vtime:t(), ari_vtime:t()}
  | {crash, name(), message | notification, ari_vtime:t(), exception()}
  | {invalid_result, name(), message | notification, ari_vtime:t(), exception()}.
-type exception() :: {error | exit | throw, term(), [term()]}.
```

`compile/1` выполняет всё, что описано в разделе «Сборка»: проверяет модули и
слоты, переводит `#graph{}` в `#program{}` и считает сводки путей. Ошибки графа
возвращаются здесь, и в прогоне их уже не встречается.
`{unknown_module, Node, Module}` означает модуль, который не загружается;
`{missing_callback, Node, Module, {Function, Arity}}` — модуль без функции
контракта узла; `{unknown_input_slot, Edge, Node, Slot}` и
`{unknown_output_slot, Edge, Node, Slot}` — ребро, конец которого называет
слот, отсутствующий в `Module:input()` или `Module:output()`. В каждой ошибке
узел и ребро названы именами из DSL.

`new/2` вызывает `init/1` каждого узла, наполняет входные очереди и ловит ошибки
адресации до первого шага. `{unknown_input, Name}` означает имя, которого нет
среди входных полурёбер, `{duplicate_input, Name}` — имя, названное в списке
дважды, `{invalid_input, Name, Item}` — элемент входа, не являющийся парой
сообщения и времени глубины узла-получателя, `{init_crashed, Name, Exception}`
— исключение при инициализации узла; результат `init/1` не той формы
считается тем же исключением с `badmatch`. `{invalid_notification, Name,
Time}` — начальный запрос с временем не той глубины, что контекст узла.
Ошибочного возврата у `advance/2` нет: нарушения временного правила,
исключения callbacks и ошибки применения их результатов попадают в
`violations/1`.

`advance(Exec, N)` выполняет до `N` шагов и возвращает состояние прогона. `done`
означает покой из раздела «Остановка», `more` — исчерпанный бюджет при
оставшейся работе. С `infinity` возвращается только `done`, а расходящийся граф
не возвращается никогда.

Состояние прогона доступно на любом ответе, поэтому `more` позволяет продолжить
с того же места, посмотреть очереди или бросить работу. Один переход выполняется
вызовом `advance(Exec, 1)`, и он же служит трассировкой: после каждого перехода
видны очереди, счётчики, запросы, `steps` и `violations`. Отдельного механизма
трассировки ядро не заводит.

`inspect/1` показывает программу или состояние прогона в виде map с ключами по
именам полей `#program{}` и `#execution{}`; записи внутри также развёрнуты в
map. Записи наружу не выходят, и тесты с пошаговой диагностикой читают этот
map.

Вход адресуется именами входных полурёбер, выход — именами выходных. Значением
служит список пар сообщения и времени; у входа это порядок загрузки, у выхода
порядок очереди.

Вход подаётся списком: вызывающий пишет его прямо в вызове. Порядок этого списка
в прогон не протекает: начальные рёбра ставятся в `ready` по `edge_order`,
затем добавляются допустимые уведомления по правилу инициализации.

`violations/1` отдаёт то, что сломалось по ходу прогона. `time_rule` описывает
нарушение правила времени узла: имя узла, вид перехода, время входа и
недопустимое время, которое узел выдал. `crash` описывает непойманное исключение
внутри callback: имя узла, вид перехода, время и тройку из класса, причины и
стека. `invalid_result` содержит те же поля для исключения при разборе или
применении результата callback. При успешном применении результата каждое
отбрасывание по временному правилу даёт одну запись `time_rule`. Отброшенный
целиком результат даёт одну запись `invalid_result`, а исключение callback —
одну запись `crash`. Список хранится в `#execution.violations` новым
нарушением в голове, чтобы добавление стоило `O(1)`; `violations/1` и
`inspect/1` разворачивают его в порядок возникновения. Счётчик получается
длиной списка.

Разовый прогон собирается из этих вызовов и живёт в тестах:

```erlang
run(Program, Inputs) ->
    {ok, Exec} = ari_local_runtime:new(Program, Inputs),
    {done, Done} = ari_local_runtime:advance(Exec, infinity),
    {ari_local_runtime:outputs(Done), ari_local_runtime:violations(Done)}.
```

## Границы первой версии

Вне модели локального runtime остаются распределение узлов по процессам и
BEAM-нодам, динамическое изменение графа, неограниченные потоковые входы и
входные фронтиры, сохранение состояния и восстановление после сбоев,
backpressure и оптимизации с переупорядочиванием сообщений.
